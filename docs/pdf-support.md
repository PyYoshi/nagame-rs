# PDF対応の採用前検証と実装方針

PDFiumと`pdfium-render`を採用する方針。Popplerは採用しない。現時点では独立した試作で描画・配布条件を検証済みで、通常のNagameへはまだ組み込んでいない。

## 検証した構成

| 項目 | 構成 |
|---|---|
| Rustラッパー | `pdfium-render = "=0.9.5"` |
| feature | `default-features = false`、`pdfium_8125`。`image`連携・`thread_safe`は使わない |
| PDFium | 158.0.8125.0（`chromium/8125`）のV8なしビルド。`pdf_enable_v8 = false`、`pdf_enable_xfa = false` |
| 読み込み | 明示した絶対パスから動的ロード。作業ディレクトリやシステムの任意版を自動探索しない |
| 出力 | `PdfBitmapFormat::BGRA`、`set_reverse_byte_order(false)`、白背景 |
| 日本語フォールバック | Noto Sans CJK JP Regularで検証。配布時のフォント構成は未確定 |

`pdfium_latest`は依存更新で指すAPIが変わるため使わず、PDFium本体とAPI featureを一緒に固定する。上記は動作確認した組み合わせであり、将来の配布でもこの版を更新せず使い続けるという意味ではない。

## 確認したことと限界

- Linux x86_64でRustラッパーによるページの描画、拡大解像度での再描画、繰り返し描画が成功した。生成したPDFでBGRAの色順、ページの90度回転、透明度の白背景への合成、CropBox、破損ファイルの拒否を確認した。
- `PdfBitmap::from_bytes`でRustが所有するバッファへ直接描画できた。`as_raw_bytes`による追加コピーを避け、GPUIへ渡すBGRAと台帳上の容量を揃えられる。
- Ubuntu 24.04の配布用コンテナーでも、同じPDFium共有ライブラリをロードして合成PDFを描画できた。確認したLinux x86_64バイナリーが要求するglibcシンボルは最大2.16で、現在の配布基準2.39を引き上げない。
- 日本語フォントを持たないコンテナーでは、非埋め込みの日本語が描画されなかった。明示した探索先へNoto Sans CJK JP Regularを配置すると描画され、合成PDFの日本語行も目視確認できた。フォント未埋め込みのPDFに対して、PDFiumを同梱するだけでは同じ表示を保証できない。
- Linux・macOS・Windowsのx86_64／ARM64向け配布物を取得し、公開されたSHA256と実ファイルのアーキテクチャを確認した。macOS・Windows・ARM64での実行、macOS Universalバイナリーの作成、各OSのパッケージングは未検証。
- 非公開の検証資料は内容の目視比較を行っていない。描画APIの成功は、字形・色・レイアウトが原本と完全一致することの保証ではない。縦書き、埋め込みフォント、暗号化、フォーム・注釈、巨大ページ等は追加の専用テストが必要。

## 本体への組み込み

### ページの識別とナビゲーション

現在の`Album.paths`は1ファイルを1画像として扱う。PDF対応では、ファイルパスとページ番号を組にしたページ識別子を導入する。同じPDFの各ページをファイル名で並べ替えない。フォルダーの画像一覧とPDF内のページ一覧を区別し、ページの先頭・末尾での操作も明示する。

見開きは同じ文書の隣接ページを使う。横長単独表示の判定には、PDFの回転とCropBoxを反映した寸法を使う。先頭・末尾の端数、RTL／LTR、単独表示への切り替え、前後移動を既存の画像経路と同様に検証する。

### 専用ワーカーとメモリー

PDFiumの初期化、文書・ページ・ビットマップの作成と破棄を、1本の専用スレッドに集約する。UIや通常画像のデコードスレッドへPDFiumのハンドルを渡さない。`thread_safe` featureに依存せず、PDFiumを呼ぶスレッド自体を限定する。

現在ページを先読みより優先し、要求には世代を付ける。古い描画結果は採用しない。文書を毎ページ開き直さず、同じ文書のハンドルを再利用し、文書の切り替え・更新・メモリー逼迫時には破棄する。途中中断の必要性とprogressive renderingの採用は、長時間かかるページで判断する。

出力バッファは割り当て前に寸法・乗算のオーバーフロー・`memory::Budget`を検査し、保持中は`Ledger`へ登録する。PDFium内部の文書・フォント・デコード用メモリーは画素台帳だけでは制限できない。保持量とRSSを別々に計測する。既存のglibc設定と解放後のtrimは、試作でもRSSを下げるのに有効だった。

### ズームと保存

ページの論理寸法と描画バッファのピクセル寸法を分ける。初回は画面とデバイススケールに必要な解像度で描画し、拡大時は古い画像を表示しながら非同期で再描画する。キャッシュキーには文書の更新情報、ページ番号、描画寸法、回転等を含める。全ページを起動時に画像化しない。

PDFページには画像ファイルのような一意の元ピクセル寸法がない。画像として保存・コピーする場合は、表示用キャッシュとは独立して出力解像度を決める。PDF編集やPDF形式への書き戻しは、閲覧対応とは別の機能として扱う。

## 配布

LinuxではAppDir内の`libpdfium.so`、Windowsではアプリ同梱の`pdfium.dll`、macOSではアプリバンドル内の`libpdfium.dylib`を明示してロードする。PDFiumを見つけられない場合はPDFを開く操作にエラーを返し、通常画像の閲覧まで停止させない。

今回確認した配布物は、Google公式のバイナリーではなく[bblanchon/pdfium-binaries](https://github.com/bblanchon/pdfium-binaries)によるビルド。本体へ導入するときは版・CPU・SHA256・出所をロックし、実行時の自動ダウンロードは行わない。Linux x86_64の確認済みアーカイブは`pdfium-linux-x64.tgz`、SHA256は`e1c3ce6e270cb5e0c20816b379ad9f2c1309972697c505f508de92bf5e7d6659`。

PDFium本体・配布物の`LICENSE`だけでなく、`licenses/`の第三者ライセンスも同梱する。`pdfium-render`はMIT／Apache-2.0。フォントを同梱する場合は、その版とライセンスも記録する。PDFiumはUbuntuのapt由来ではないため、現在のネイティブライブラリー収集とは別に、由来と配布条件を管理する必要がある。

## 検証資料の扱い

公開できない資料をリポジトリー、`target`、テストfixture、配布用ソースアーカイブへコピーしない。資料のファイル名、著者・タイトル等のメタデータ、本文、ページ画像をログ・文書・スクリーンショット・コミットへ残さない。原本を読み取り、描画結果はメモリー内で処理する。回帰テストはコードで生成する合成PDFを使い、エラーの検証でも利用者のパスやメタデータを出力しない。
