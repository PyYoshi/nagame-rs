# PDF対応の検証と実装方針

PDFiumと`pdfium-render`を採用する。独立した試作で描画・配布条件を検証し、[段階](#段階)の1を本体へ組み込んだ。本書は選定理由、試作と組み込みで確認したこと、設計、決定事項と未決事項をまとめる。実装の契約は [コード構成と設計](architecture.md#pdf) にもまとめている。

## 選定

| 候補 | 判断 | 理由 |
|---|---|---|
| PDFium（`pdfium-render`） | 採用 | Chrome由来で互換性・速度が高い。BGRAへ直接描画でき、JBIG2・JPX・CCITTのデコーダーを内蔵する。BSD-3-Clause／Apache-2.0で、同梱の第三者ライブラリーを含めGPLv3と両立する |
| hayro | 保留 | 純Rustでネイティブ依存がなく、メモリー安全性と配布の面で有利。ただし0.9.0では非埋め込みフォントの代替検索が未対応で、標準14フォントにしか置き換えられないため、非埋め込みの日本語を描けない。代替フォントに対応したら再評価する |
| MuPDF（`mupdf` crate） | 不採用 | AGPL-3.0。C/C++の同梱ビルドにlibclangが必要で、JavaScriptが既定で有効 |
| Poppler（`poppler-rs`） | 不採用 | Ubuntuのパッケージで既存のライブラリー収集に乗る利点はあるが、cairo・glib・gioが必須で、描画はcairo経由に限られ、`Page` が `Send` でない |

## 検証した構成

| 項目 | 構成 |
|---|---|
| Rustラッパー | `pdfium-render = "=0.9.5"` |
| feature | `default-features = false`、`pdfium_8125`。`image`連携・`thread_safe`は使わない |
| PDFium | 158.0.8125.0（`chromium/8125`）のV8なしビルド。`pdf_enable_v8 = false`、`pdf_enable_xfa = false` |
| 読み込み | 明示した絶対パスから動的ロード。作業ディレクトリやシステムの任意版を自動探索しない |
| 出力 | `PdfBitmapFormat::BGRA`、`set_reverse_byte_order(false)`（既定のtrueではRGBAになる）、白背景 |
| 日本語フォールバック | Noto Sans CJK JP Regularで検証。探索先と配布時のフォント構成は [フォント](#フォント) を参照 |

`pdfium_latest`は依存更新で指すAPIが変わるため使わず、PDFium本体とAPI featureを一緒に固定する。上記は動作確認した組み合わせであり、将来の配布でもこの版を更新せず使い続けるという意味ではない（[安全性](#安全性)）。

## 確認したことと限界

- Linux x86_64でRustラッパーによるページの描画、拡大解像度での再描画、繰り返し描画が成功した。生成したPDFでBGRAの色順、ページの90度回転、透明度の白背景への合成、CropBox、破損ファイルの拒否を確認した。
- `PdfBitmap::from_bytes`でRustが所有するバッファへ直接描画できた。`as_raw_bytes`による追加コピーを避け、GPUIへ渡すBGRAと台帳上の容量を揃えられる。
- Ubuntu 24.04の配布用コンテナーでも、同じPDFium共有ライブラリーをロードして合成PDFを描画できた。確認したLinux x86_64バイナリーが要求するglibcシンボルは最大2.16で、現在の配布基準2.39を引き上げない。
- 日本語フォントを持たないコンテナーでは、非埋め込みの日本語が描画されなかった。明示した探索先へNoto Sans CJK JP Regularを配置すると描画され、合成PDFの日本語行も目視確認できた。フォント未埋め込みのPDFに対して、PDFiumを同梱するだけでは同じ表示を保証できない。
- Linux・macOS・Windowsのx86_64／ARM64向け配布物を取得し、公開されたSHA256と実ファイルのアーキテクチャを確認した。macOS・Windows・ARM64での実行、macOS Universalバイナリーの作成、各OSのパッケージングは未検証。
- 非公開の検証資料は内容の目視比較を行っていない。描画APIの成功は、字形・色・レイアウトが原本と完全一致することの保証ではない。縦書き、埋め込みフォント、暗号化、フォーム・注釈、巨大ページ等は追加の専用テストが必要。

ソースで確認した `pdfium-render` 0.9.5 の性質:

- 段階描画（`FPDF_RenderPageBitmap_Start` 等）は低レベルのバインディングだけで、高水準APIはない。
- `FPDF_SetSystemFontInfo` は、高水準の `Pdfium::set_custom_font_provider`（`PdfiumCustomFontProvider` トレイト）から使える。
- `PdfPageImageObject::get_raw_image_data` はフィルターを適用しない埋め込み画像の生データ、`filters` はそのフィルター一覧を返す。
- `PdfiumLibraryConfig::set_user_font_paths` はPDFiumの `FPDF_LIBRARY_CONFIG` の `m_pUserFontPaths` へ渡す。PDFiumの仕様では、このパスは既定の探索先の代わりに使われる。

## 本体への組み込み

### 範囲

以下の「初版」は、本体への最初の組み込み（[段階](#段階)の1）を指す。初版はページを画像として眺めることに限る。テキストの選択・検索、リンク、フォーム入力、注釈の編集、しおり（目次）による移動、パスワード入力、印刷、PDFの編集、PDF形式での保存・書き戻しは扱わない。PDFの編集・書き戻しは閲覧とは別の機能として扱う。利用者パスワードで暗号化されたPDFはエラーを表示する。

### 閲覧モデル

組み込み前の`Album.paths`は1ファイルを1画像として扱っていた。PDFは**ページを持つ入れ物**として扱い、ファイルパスとページ番号を組にしたページ識別子 `model::Entry` で一覧を持つ（`Album.entries`）。`Entry` にはページの論理寸法も持たせる。未実装の書庫（zip/cbz）も同じ形で載るようにし、PDF専用の分岐を増やさない。

- PDFを開くと、アルバムはそのPDFのページ列になり、`Album.directory` はPDFのパスになる。並びは常に文書順で、並び順・数値順・逆順・ランダムの設定を適用しない。
- 一覧の解決時に、補助プロセスでPDFを開いてページ数と全ページの論理寸法を一度に取得し、`Entry` に入れる。一覧の解決・情報画面・横長判定はこの値を使い、描画以外でPDFを読み直さない。
- 対応画像の判定（`supported`）とは別に、入れ物の判定を設ける。フォルダーの画像一覧にはPDFを含めない。
- フォルダーの探索（`directories`・`next_directory`）は、サブフォルダーとPDFを同格の入れ物として自然順に並べる。PDFは子を持たない入れ物として扱う。
- 開けないPDF（破損・利用者パスワード・0ページ・PDFium不在）は、画像のないフォルダーと同じく、画像がある前後のフォルダーを探す移動では飛ばす。直接開いた場合は理由をエラー表示する。同階層の隣接移動では空の一覧として移って理由を表示し、次の移動でその先へ進める。
- ページの先頭・末尾での操作は、既存の境界の設定（確認・回り込み・フォルダー移動・停止）に従う。自動移動と確認ダイアログは `continue_to_folder` を通り、戻る方向は移動先の末尾、進む方向は先頭を選ぶ。巻ごとのPDFを続けて読める。↑↓とAlt+↑の直接操作は、既存の `previous_folder_first`・`parent_folder_first` に従う。
- 親フォルダー（Alt+↑）はPDFのあるフォルダーを開く。
- 画像がなくPDFだけがあるフォルダーは、ファイル選択・引数・ドロップで開いたときだけ先頭のPDFを開く。親フォルダーへの移動では開かない（直前のPDFへ戻ってしまうため）。
- 対応形式の判定、ドロップ、開くダイアログ、引数に `.pdf` を加える。

見開きは同じ文書の隣接ページを使い、余った最終ページは単独表示にする。横長単独表示の判定には、`Entry` の論理寸法（PDFの回転とCropBoxを反映する。取得APIが`/Rotate`を含むかはテストで確認する）を使う。先頭・末尾の端数、RTL／LTR、単独表示への切り替え、前後移動を既存の画像経路と同様に検証する。

### 解像度

PDFページには画像ファイルのような一意の元ピクセル寸法がない。ページの論理寸法（pt）と描画バッファのピクセル寸法を分け、次の2層で扱う。全ページを起動時に画像化しない。

当初案は初回の描画解像度を画面の大きさとデバイススケールから決め、描画寸法をキャッシュキーに含めていた。これを、画面に依存しない基準解像度と、表示専用の描き直しに分けた。画面に依存すると、ウィンドウの大きさの変更・先読み・見開きのたびに描き直しが要り、スキャンしたページの元の画素を原寸・保存に使えないため。

**基準解像度**はページごとに1つ決め、その解像度で描いた画像を `Loaded.image` とする。

| ページ | 基準解像度 |
|---|---|
| 画像主体（1枚の画像がページ面積の90%以上を覆い、他に見える文字・図形がない。OCR用の不可視テキストは数えない） | その画像の実効解像度（画素数÷配置寸法） |
| それ以外（文字・図形を含む） | 基準DPI（暫定150。A4で約1240×1754、8.7 MB）と、ページ内の画像の実効解像度の大きい方 |

- 描画前に寸法・乗算のオーバーフロー・`Budget::still`・1辺16,384を検査し、超えるなら縮める。逼迫中は `Budget::still` が下がるため、縮めた結果には印を付け、予算が戻った後にキャッシュから取り出したときは描き直す。
- 見開きの2ページは共通の倍率で描く。`compose` は画素の幅を足して高さの大きい方に揃えるため、基準解像度の違うページをそのまま並べると大きさが揃わない。2ページの基準解像度の大きい方で描き、合成後が上限を超えるなら両方を同じ比率で縮め、その倍率を合成結果のキーに含める。
- `Loaded.dimensions` が画素寸法と一致する既存の不変条件を保つので、見開き合成・追加回転・LRU・先読み・台帳をそのまま使える。
- 原寸（1）は基準解像度の1:1。画像主体のページでは埋め込み画像の画素と一致する。
- 保存・コピーは基準解像度の画像を使い、表示用の描き直しの結果は使わない。当初案の「表示用キャッシュとは独立して出力解像度を決める」を、表示の描き直しから独立した基準解像度として具体化した。単独表示のページで縮めた印がある場合は、逐次デコード中のGIFの保存と同じく、元ファイルから基準解像度で描き直して書き出す。出力解像度を選ぶUIは後回しにする。
- キャッシュキーには文書の更新日時・大きさ、ページ番号、回転、見開き条件、基準解像度の決め方の版を含める。画面の寸法は含めないので、ウィンドウの大きさを変えても描き直さず、先読みも画面に依存しない。

文字・図形を含むページのフィットは、`fit_upscale` の設定によらず画面に合わせる。固有の画素寸法がなく、基準DPIで描いた画素数がウィンドウの論理寸法より小さい場合（1倍表示の4K等）に、拡大しないフィットではウィンドウより小さく表示されるため。画像主体のページと通常の画像は従来どおり設定に従う。

**表示解像度での描き直し**は、文字・図形を含むページで、表示に必要なデバイスピクセルが基準解像度より大きい場合（拡大、高解像度画面でのフィット）だけ行う。フィットで拡大するため初版に含める。保存・コピーに使わない表示専用の派生画像で、`resample` の補間結果と同じ規則に従う。ただし `resample::State` は既定のGPU表示では何もしないので、表示補間の方式によらない専用の状態を設ける。

- 要求の変更から60ms後に描き、元画像のIDと要求した出力寸法が一致する結果だけを採用する。描き終わるまでは基準画像を拡大して表示する。
- 台帳に登録し、`Budget::resample` を超える場合は基準画像の表示へ戻る。2回目の逼迫では補間結果と同じく捨てる。置き換えた画像は `Viewer.retired` へ移し、2フレーム後に解放する。
- 画像主体のページは描き直さない（情報が増えない）。拡大・縮小は既存の補間設定に従う。
- 1辺16,384を超える倍率では表示範囲だけを描く（タイル）。初版は上限で止める。

**高速経路**（計測の結果、採用を見送った）: 画像主体のページで、生データ（`get_raw_image_data`）を既存のJPEGデコーダーで復号する案。2026-11-07のリリースビルドの計測では、600 DPIのA4（4960×7016画素）をPDFiumで描いて本体へ渡すまで約345 ms、同じJPEGをimageクレートで復号するだけで約166 msだった。約4割速いが、`pdfium-render` 0.9.5のAPIではマスク（SMask・Mask）とDecode配列を調べられず、反転・切り抜きのある画像を取り違えないと保証できない。連続して読むときは先読みで隠れる差のため、正しさを優先して見送る。条件を検査できるAPIが使えるようになったら再検討する。検討した条件は次のとおり。

- 1枚の画像がページ全体を覆う。
- フィルターがDCTDecodeだけで、マスク・Decode配列がなく、色空間がDeviceRGBかDeviceGray（Adobe CMYKは対象外）。
- 配置が軸に平行で反転がなく、`/Rotate` が0で、CropBoxがMediaBoxと同じ。

PDFはJPEG内のEXIFの向きを使わないため、この経路では復号時に向きを適用しない。

### 補助プロセスと中断

PDFiumは初版から補助プロセスで動かす（[安全性](#安全性)）。PDFiumの初期化、文書・ページ・ビットマップの作成と破棄は、補助プロセスの1本のスレッドだけが行う。Nagame本体はPDFiumをロードせず、ハンドルも持たない。`thread_safe` featureに依存せず、PDFiumを呼ぶスレッド自体を限定する。

- Linuxでは、補助プロセスとして同じ `nagame` を `/proc/self/exe` から隠しの引数で起動し、GPUIを初期化しない。最初のPDFを開くときに起動し、PDFを閉じても次の文書のために残す。
- 本体とはUnixドメインソケットの組（socketpair）でつなぐ。要求と応答はハンドルを含まない平文のデータ（ページ・寸法・回転・世代／寸法・エラーの種類）に限る。
- 本体が開いたPDFのファイル記述子を渡し、補助プロセスは `load_pdf_from_reader` で読む。補助プロセスがパスを開く必要をなくし、ファイルアクセスを絞れるようにする。
- 補助プロセスはmemfdを `PdfBitmap::from_bytes` の出力先にしてBGRAで描き（strideが幅×4と一致することを確認する）、ファイル記述子を本体へ渡す。本体は1回コピーして `RenderImage` にする。
- 本体側では1本の仲介スレッドが送受信と要求の優先順位を受け持つ。`pipeline` ワーカーはGIFの `Stream::first` と同様に、結果か中止まで待つ。描いた画像は通常の画像と同じキャッシュ・台帳へ入る。
- 要求には世代を付け、古い描画結果は採用しない。要求は種類（現在ページ、現在ページの表示解像度、先読み）ごとに最新の1件だけを持ち、この順に処理する。新しい要求は、同じ種類の未着手の要求だけを置き換える。
- 先読みは前後のページ。見開きでは次の見開き（2ページ先から）を読む。通常画像の見開きの先読みも現在は前後1枚なので、合わせて見直す。
- 文書を毎ページ開き直さず、直近の文書のハンドルを再利用する。文書の切り替え・更新・メモリー逼迫時には破棄する。
- 段階描画（progressive rendering）は採用しない。2026-11-07の計測で、補助プロセスの起動は約17 ms、1000ページの合成PDFを開き直すのは約8 ms、図形20万個の重いページの描画は約315 msだった。待つ人がいない長い描画は補助プロセスを止めて打ち切れば足り（下記）、低レベルのバインディングで一時停止のコールバックを扱う複雑さに見合わない。
- 補助プロセスが異常終了したら、次の要求で起動し直す。そのページは描画できなかったことを表示し、同じページで続けて異常終了した場合は再試行しない。待機中に終わっていた補助プロセスは失敗に数えない。1件の描画が制限時間（初期値20秒）を超えたら停止させて起動し直す。時間切れのページは先読みと表示解像度の描き直しでは試さず、利用者が開いたときだけ試し直す。F5は文書の失敗の記録を消す。
- 待つ人がいなくなった描画が1秒を超えて続き、別の要求が待っている場合は、補助プロセスを止めて先へ進む。重いページの先読みで、次の操作が待たされ続けないようにするため。

### メモリー

出力バッファは割り当て前に寸法・乗算のオーバーフロー・`memory::Budget`を検査し、保持中は`Ledger`へ登録する。PDFium内部の文書・フォント・デコード用メモリーは補助プロセスにあり、画素台帳だけでは制限できない。本体の保持量と補助プロセスのRSSを別々に計測する。補助プロセスには `RLIMIT_DATA` でメモリーの上限（初期値はRAMの1/4を1〜4 GiBに収めた値）を設ける。逼迫の段階1で開いている文書を閉じさせ、段階2で停止させる（次の要求で起動し直す）。既存のglibc設定と解放後のtrimは、試作でもRSSを下げるのに有効だった。

### 既存機能との接続

- ページは白で塗ってから描く。透明のままでは暗い背景で文字が読めない。
- 情報画面には、ページ番号／総数、ページの論理寸法（mm）、表示画像の画素数と基準解像度（DPI）、ページの種類（画像主体か文字・図形を含むか）を出す。
- 保存の既定ファイル名は既存の `{名前}_view.png` に合わせ、ページ番号を含める（例: `{文書名}_p012_view.png`、見開きは `{文書名}_p012-013_view.png`）。パスのコピーはPDFのパス。F5は文書を開き直す。
- 利用者向けの文言は `locales/{ja,en}/nagame.ftl` に置く。破損・暗号化・0ページ・PDFium不在のエラーと情報画面の項目名が対象で、PDFiumのエラーをそのまま表示しない。

### フォント

PDFiumはLinuxでfontconfigを使わず、フォントのディレクトリーを自分で走査する。

- 探索先を指定しない場合の既定は `/usr/share/fonts`、`/usr/share/X11/fonts/Type1`、`/usr/share/X11/fonts/TTF`、`/usr/local/share/fonts`。利用者のディレクトリー（`~/.local/share/fonts` 等）は含まない。
- 探索先を指定すると既定を置き換える。`pdfium-render` の `set_platform_default_user_font_paths` は `/usr/share/fonts/truetype/` と `/usr/local/share/fonts/` だけに狭めるので使わない。
- 日本語の代替は、MS・Takao・VL・IPA・Kochiのゴシック・明朝の名前を順に探す。この表にNoto CJKやSource Hanはない。どれもなければ、Shift-JISに対応するフォントから太さ・セリフ等の類似度が最も高いものを選ぶ。試作でNoto Sans CJK JPが使われたのはこの経路。

方針:

- fontconfigを使えない場合の探索先は、既定の4つに `$XDG_DATA_HOME/fonts`（未設定なら `~/.local/share/fonts`）と `~/.fonts` を加え、存在するものだけを明示する。AppImageでもホストのフォントを使う。
- 初版はフォントを同梱しない。READMEに日本語フォント（Noto CJK等）が必要なことを書く。同梱する場合は、その版とライセンスも記録する。
- 段階1の確認（2026-11-07、開発機にNoto Sans JP・Noto Serif CJK JP・M PLUS 1pを導入済み）では、PDFium既定の探索で非埋め込みのMS-Mincho・MS-Gothic（Adobe-Japan1、UniJIS-UCS2-H）を描くと、明朝の指定にも細いゴシック体が選ばれた。
- 段階2で、fontconfigで選ぶ `FPDF_SYSFONTINFO` を自前で実装した（`src/pdf/fonts.rs`）。`pdfium-render` の `PdfiumCustomFontProvider` は、UTF-8でない書体名（Shift_JISの「ＭＳ 明朝」等）を扱えず、セリフ体の判定のビット演算に誤りがあり、TTCの書体も選べないため使わない。書体名と文字セットから言語（ja・zh-cn・zh-tw・ko等）と明朝系／ゴシック系・太さを推定し、fontconfigの優先順位でその言語に対応するスケーラブルなフォントを選ぶ。TTCはWindowsのGDIのGetFontDataと同じ規約（表0は書体の位置からファイルの終わりまで、`ttcf` 表はTTC全体。短い領域にも先頭を書く）で渡し、PDFiumが長さの差から書体の番号を求める。ファイルの中身はパスごとに共有し、問い合わせの結果は記憶する。記号の文字セットとよく使われる記号フォント（Wingdings等）はPDFium内蔵のフォントを使う。書体名による明朝系／ゴシック系の推定は日中韓の書体だけに使い、欧文はPDFのフラグに従う。権限を絞った後に開けない候補（フォントのディレクトリー外を指すシンボリックリンク等）は選ばない。fontconfigにフォントが1つもなければ導入しない。fontconfig（GPUIが実行時に読み込む `libfontconfig.so.1`）を使えない場合は、PDFium既定の探索に戻る。
- 可変フォントについて：PDFiumは名前付きインスタンスを選べず、既定のインスタンスで描く（Fedoraの `NotoSerifCJK-VF.ttc` はExtraLight、`NotoSansCJK-VF.ttc` はThin）。そこで、先頭の候補が可変フォントなら、同じデザインの静的なフォント（例：Noto Sans CJK JPに対するNoto Sans JP）を優先する。別のデザインには替えない（字形が変わるため。実際にDroid Sans Fallbackへ替えると中国語寄りの字形になった）。
- 段階2の確認（同じ開発機）：明朝の指定はNoto Serif CJK JP（可変フォントの既定、細め）の明朝体、ゴシックの指定はNoto Sans JP Regularで描かれた。欧文のHelveticaはfontconfigの別名設定によりNimbus Sansになった。選んだフォントは `NAGAME_PROFILE=1` で補助プロセスの標準エラーへ出る。

### 安全性

PDFは攻撃面が広い。PDFiumのメモリー安全性の脆弱性は継続的に見つかり、Chromeの更新で修正されている。版を固定する以上、上流の更新を追い、セキュリティ修正を取り込んだらNagameも配布し直す運用が要る。

- V8・XFAなしのビルドを使い、明示した絶対パスだけからロードする。
- 初版から補助プロセスで描く（[補助プロセスと中断](#補助プロセスと中断)）。PDFiumの異常終了とハングが本体へ及ばず、停止させれば内部のメモリーも確実に回収できる。C/C++のlibheifはプロセス内のまま。
- 補助プロセスはPDFiumとフォントの準備の後に権限を絞る（`src/pdf/sandbox.rs`）。Landlockでファイルの読み取りをフォントのディレクトリーだけにし、書き込み・実行・作成、TCPの接続・待ち受け、同じ制限の外へのシグナルと抽象Unixソケットを禁止する。seccompでプロセスの生成・プログラムの実行・pidfd等による他のプロセスの操作（本体の記述子の取り出しを含む）・新しいソケット・名前空間やカーネル管理系の呼び出しをEPERMで拒否する（スレッドの作成は許す）。Landlockの許可にはシンボリックリンクの実体のディレクトリーも含め、規則を1つも登録できなければ制限を掛けない（フォントを読めなくしない）。どちらもカーネルの対応に依存し、使えない環境では制限なしで続ける。開発機（Linux 7.2）ではLandlockのABI 10とseccompが有効だった。外部のクレートは使わず、カーネルのUAPIの定義を自前で持つ。

### 配布と開発環境

LinuxではAppDir内の`libpdfium.so`、Windowsではアプリ同梱の`pdfium.dll`、macOSではアプリバンドル内の`libpdfium.dylib`を明示してロードする。探索先は実行ファイルの位置から決め、作業ディレクトリは見ない。ロードするのは補助プロセスだけ。PDFiumを見つけられない場合はPDFを開く操作にエラーを返し、通常画像の閲覧まで停止させない。AppImageでは補助プロセスもマウント中の同じバイナリーとAppRunの環境を引き継ぐので、`just dist-check-appimage` でPDFの描画まで確認する。

今回確認した配布物は、Google公式のバイナリーではなく[bblanchon/pdfium-binaries](https://github.com/bblanchon/pdfium-binaries)によるビルド。本体へ導入するときは版・CPU・SHA256・出所をロックし、実行時の自動ダウンロードは行わない。Linux x86_64の確認済みアーカイブは`pdfium-linux-x64.tgz`、SHA256は`e1c3ce6e270cb5e0c20816b379ad9f2c1309972697c505f508de92bf5e7d6659`。上流のワークフローは `actions/attest-build-provenance` で出所の証明を作り、`pdfium-attestation.json` としてリリースに添付する。取得時はSHA256に加えて `gh attestation verify <archive> --repo bblanchon/pdfium-binaries` で確認する。2026-11-07に、固定したアーカイブでこの検証が成功した（`tools/fetch_pdfium.py` は `gh` があれば毎回検証する）。

PDFium本体・配布物の`LICENSE`だけでなく、`licenses/`の第三者ライセンスも同梱する。`pdfium-render`はMIT／Apache-2.0。PDFiumはUbuntuのapt由来ではないため、現在のネイティブライブラリー収集とは別に、由来と配布条件を管理する。`build-info.json` にPDFiumの版とSHA256を記録し、`SOURCE.md` に差し替え方法を書く。

開発環境:

- `just pdfium`（[tools/fetch_pdfium.py](../tools/fetch_pdfium.py)）が [pdfium.json](../packaging/linux/pdfium.json) の版を取得してSHA256を照合し、`target/pdfium/` へ展開する。`cargo run`・`cargo test` には [.cargo/config.toml](../.cargo/config.toml) の `[env]` が `NAGAME_PDFIUM_LIBRARY` を渡す。
- `cargo test --locked` の前提が増えるため、AGENTS.mdと開発文書へ手順を書く。
- PDFiumがない場合のPDFのテストは、スキップで成功に見せず失敗させる。

### テスト

回帰テストには、コードで生成する合成PDF（`pdf::synthetic`）を使う。ページ・図形・無圧縮の画像・文字（不可視を含む）・`/Rotate`・CropBox・暗号化の辞書を直接書く。テストではテストバイナリー自身を補助プロセスとして起動し直すので、プロセスの分離と通信も実物で通る。

| 種類 | 自動テストで確認すること |
|---|---|
| 描画と寸法（`pdf`） | JPEG（DCTDecode）のスキャンの埋め込み解像度、回転とCropBoxを反映した論理寸法、BGRAの色順・白背景・`/Rotate`、画像主体の判定（不可視テキストだけなら画像主体、見える文字なら文字・図形、フォームXObjectで包んだスキャン）と基準解像度、上限での縮小、指定倍率 |
| エラー（`pdf`） | 暗号化・破損・0ページ・範囲外のページ・存在しないファイル、PDFiumを読み込めない補助プロセス |
| 補助プロセス（`pdf`） | Landlock・seccompの制限（フォント以外の読み取り・プロセス生成・ソケットの拒否）と制限後の描画、異常終了からの再起動と、同じ文書で続けて異常終了したときの再試行の停止、制限時間を超えた要求の停止と再起動、時間切れの文書を先読みで試さないこととF5での消去、待つ人がいない長い描画の中断、メモリー上限（`RLIMIT_DATA`）、待つのをやめた要求、要求の優先順位と置き換え |
| 閲覧（`model`） | 文書順のページ列と並べ替えないこと、見開きの先読み、入れ物としてのPDFの探索（開けないPDFを飛ばす・隣接移動では空の一覧と理由を示して先へ進める）、PDFだけのフォルダーを選んだときと親フォルダーへの移動 |
| フォント（`pdf::fonts`） | Shift_JISを含む書体名と文字セットからの言語・明朝／ゴシック・太さの推定、可変フォントより同じデザインの静的なフォントを優先すること、TTCの書体と表の取り出し |
| 見開きの描き直し（`resample`） | 2ページを共通の倍率で描き、左右開きの向きに並べること |
| キャッシュ（`pipeline`） | 基準解像度での読み込み、先読みしたページのキャッシュ、基準解像度の違う見開きの倍率合わせと上限での縮小、逼迫中に縮めたページを逼迫後に使わないこと |
| 実ウィンドウ（`ui_smoke`） | 文字のページのフィットと表示解像度での描き直し、200回のページ送り、見開き、逼迫で止めた補助プロセスからの回復、フォームXObjectで包んだスキャン、最終ページから次のPDFへの移動 |
| AppImage（`check_appimage.py`） | 同梱した `libpdfium.so` とライセンス、隔離環境での合成PDFの読み込み |

自動化していない確認: 非埋め込みの日本語フォント（ホストのフォントに依存。[フォント](#フォント)の確認結果を参照）、実際のスキャン本・文字のPDFでの見た目と速度、利用者が操作するときの保存・情報画面。

## 検証資料の扱い

公開できない資料をリポジトリー、`target`、テストfixture、配布用ソースアーカイブへコピーしない。資料のファイル名、著者・タイトル等のメタデータ、本文、ページ画像をログ・文書・スクリーンショット・コミットへ残さない。原本を読み取り、描画結果はメモリー内で処理する。回帰テストはコードで生成する合成PDFを使い、エラーの検証でも利用者のパスやメタデータを出力しない。
