# 多言語対応の設計とライブラリ選定

## 採用する構成

Fluent形式のメッセージを、`i18n-embed` と `i18n-embed-fl` で扱う。日本語と英語に対応する。初回・言語指定のない既存設定ではOSの主言語を使い、日本語なら日本語、それ以外や取得できない場合は英語にする。設定の「表示・漫画 → 表示言語」（Display & manga → Language）で「システムに合わせる／日本語／English」を選べる。変更は保存後に適用し、次回起動時も保存した指定を優先する。

- [locales/ja/nagame.ftl](../locales/ja/nagame.ftl): 日本語のメッセージ。
- [locales/en/nagame.ftl](../locales/en/nagame.ftl): 英語のメッセージ、名前付き変数、複数形、表示状態による分岐。
- [i18n.toml](../i18n.toml): 英語を基準・フォールバックに指定し、リソースのドメインを `nagame` に固定する。
- [src/i18n.rs](../src/i18n.rs): 埋め込みリソースの共有ローダー、`tr!`、言語選択、情報画面や状態表示の引数の受け渡し。
- [Cargo.toml](../Cargo.toml): `i18n-embed 0.16`、`i18n-embed-fl 0.10`、`rust-embed 8`。解決版はCargo.lockに従う。

`rust-embed` の `debug-embed` を有効にし、開発ビルドも翻訳をバイナリへ埋め込む。実行時の作業ディレクトリや翻訳ファイルの配置に依存しない。通常アプリと `decode-bench` が同じエラーメッセージを共有する。

## 比較した候補

2026-11-07に公式資料と配布ソースを確認し、rust-i18nとFluent系は独立した小さなプログラムでも挙動を比較した。gettextとfluent-templatesは資料・ソースの比較で、Nagameへの組み込み試験はしていない。

| 候補 | 確認した利点 | 今回の判断 |
|---|---|---|
| rust-i18n | JSON/YAML/TOML、コンパイル時の埋め込み、英語へのフォールバック、簡単な呼び出し | キーと引数の不足がコンパイルを通り、実行時にキーや `%{name}` が残った。調査した補間実装は文字列置換で、FluentのCLDR複数形に相当する処理はない。採用しない |
| fluent-bundle単体 | Fluentの構文・変数・複数形を処理し、整形時のエラーも取得可能 | 埋め込み、言語フォールバック、呼び出し箇所の検証を別途用意する必要がある。今回は上位ライブラリと組み合わせる |
| fluent-templates | Fluentファイルの埋め込みとフォールバックがある | 参照したStaticLoaderの検索APIはキーと引数を実行時に扱う。今回重視する呼び出し箇所の検証にはi18n-embed-flを選ぶ |
| i18n-embed + i18n-embed-fl | Fluent、英語へのフォールバック、スレッド共有可能なローダー、基準翻訳のキーと名前付き引数のコンパイル時照合 | 採用。ただし全引数を省略した場合などの検証の穴は下記のテストで補う |
| gettext-rs | PO/MOの翻訳作業、文脈、複数形を扱う既存の仕組み | MOへの変換・配置とネイティブgettext連携が加わる。現在の単一バイナリ中心の配布にはFluentの埋め込みが合うため採用しない |

rust-i18n 4.2.4を最初に依存解決した際は、間接依存のserde-saphyr 1.3.0がRust 1.89を要求した。3.1.5も比較したが、上記のキー・引数検証と複数形の要件からFluentを選んだ。rust-i18n全体がRust 1.88で使えない、という判断ではない。

Fluent側は追加のネイティブライブラリを要求しない。`i18n-embed` は `fluent-system`・`rust-embed`・`desktop-requester` を有効にし、gettext・ファイル監視は有効にしていない。OSの主言語の取得はdesktop-requesterを使い、対応言語への対応付けはNagame側で行う。依存更新時はプロジェクトの `rust-version = "1.88"` との整合性を確認する。今回の実行検証は既存のRust 1.99.1環境であり、Rust 1.88そのものを使ったビルド試験ではない。

## 実装と実測で確認した範囲

- `fl!` は存在しないキー、誤った名前付き引数、一部の必須引数の不足をコンパイルエラーにした。
- **全引数を省略した呼び出しはコンパイルを通した。** 引数をHashMapで渡す形式も引数名のコンパイル時検証対象外。Nagameの `tr!` はリテラルキーと名前付き引数を使う。
- rust-i18n 3.1.5は、存在しないキーと引数不足の両方をコンパイル時に拒否せず、未解決の文字列を返した。
- 両方式で、Unicodeやプレースホルダーに似た文字を含む引数が再解釈されないことを確認した。
- Fluentでは数値引数から英語の単数・複数形を選べた。英語へのフォールバックと、8スレッドからの同時呼び出しも確認した。

Fluentのローダーは構文エラー等をログへ出し、一部のリソースを読み込んで続行する場合がある。また、`fl!` が照合するのは英語の基準リソースであり、将来の全翻訳の完全性を保証するわけではない。

そのため `src/i18n.rs` のテストで両言語のFTL構文、キーの重複、キー集合の一致、全メッセージの整形、引数なしの呼び出しに変数が不要なことを検査する。加えて単数・複数形、フォールバック、OS言語の対応付け、手動指定の優先、並行呼び出し、利用者のファイル名の保持を検査する。これらは `just test` / `just check` に含まれる。

## メッセージを追加するとき

画面へ表示する文言はFTLへ追加し、Rust側から次のように参照する。

```rust
tr!("open-image")
tr!("error-status", error = error)
```

動的なキー生成、文章の断片の連結、Rust側での `count == 1` による翻訳分岐は避ける。数値を使う複数形はFTLのselect式へ渡す。画像寸法などのデータ計算と、説明文の語順・句読点は分ける。

fluent-rs（fluent-bundle）の数値書式は `useGrouping` を実装せず桁区切りを付けないため、情報画面の数値はRust側（`i18n.rs`）で文字列に整形してから渡す。5桁以上の整数は3桁ごとにカンマで区切り、4桁以下（1920 × 1080 など）は区切らない。ファイルサイズは1000倍ごとの単位（KB・MB・GB・TB・PB・EB。1 MB = 1,000,000バイトで、macOSやGNOMEのファイル表示と同じ）を整数で四捨五入した概数と、区切り付きの正確なバイト数を並べる。1024倍ごとのMiB・GiBは、メモリー上限の設定と展開上限のエラーに使う。単位と数字の並びは両言語で共通にし、括弧と「バイト」「bytes」の語は翻訳側に置く。整形済みの文字列は複数形の選択に使えないため、英語の単数・複数形には別に数値（`count`）を渡す。fl!が引数をコンパイル時に照合するのは英語の文言だけなので、日本語の文言が英語にない変数を参照していないかはカタログのテストで確かめる。

翻訳文字列を設定JSONの値やUI要素IDに使わない。設定のenum名とショートカット名は既存のsnake_caseを維持し、UIのIDはCommandや列挙値・行番号を使う。

Fluentの双方向テキスト分離を有効なまま使う。変数の周りには不可視の分離文字が入ることがあるが、ファイルを開く・保存する・パスをコピーする操作には元のPathを使う。OSやコーデック由来のエラー詳細は、そのライブラリが返す文言のまま表示する。

設定JSONの `language` は `"system"`・`"ja"`・`"en"` で保存する。不足時は `system` を補い、読み込みだけで既存ファイルは書き換えない。OSの言語が実行中に変わった場合の自動追従は行わず、起動時または設定適用時に解決する。

新しい言語を追加する場合は `locales/<言語タグ>/nagame.ftl` を作り、Languageの列挙、設定の候補、OS言語との対応付けと各言語の検証を追加する。英語の基準翻訳は残す。レイアウト・複数形・変数の対応は言語ごとに確認する。
